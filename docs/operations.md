# Operations

## Environment variables

Set them in Vercel › Project › Settings › Environment Variables, for Production. Nothing secret is ever committed, and no secret needs a terminal: a secret is created in that screen (type **Sensitive**), its value drawn by a password manager's generator (1Password, Bitwarden: letters and digits, the length given below), never typed by hand. **A change takes effect only after a redeploy** (Vercel › Deployments › the latest › ⋯ › Redeploy): until then the running salon keeps the old value.

| Variable | Required | What |
|---|---|---|
| `LX_MODE` | production | `production` for the real salon. Anything else runs the **demo** (seeded salon, simulated SMS and payments, demo access shown on the login screen). |
| `SESSION_SECRET` | production | 64 random letters and digits. Signs cookies and client links. Changing it signs everyone out and invalidates links already sent. It also derives the codes of gift cards bought online: after a change, their pages say « demande ton code au salon » and only « Annuler et réémettre » gives a new code. Without it, production answers every `/api` route with 503 « Configuration incomplète : SESSION_SECRET ». |
| `SETUP_TOKEN` | first start | One-time code asked by the setup screen (« Code d’installation ») to create the owner account, so nobody else can claim an empty installation. The provider gives it to the owner, then removes it (the Comptoir warns while it is still set). |
| `DATABASE_URL` (or `POSTGRES_URL`) | production | Postgres (Neon or Supabase from the Vercel marketplace, **EU region**). Set by the marketplace; tables are created on first start. |
| `BLOB_READ_WRITE_TOKEN` | alternative | Vercel Blob instead of Postgres. `LX_BLOB_PREFIX` (default `lx2`), `LX_BLOB_ACCESS` (`private` default). With Postgres too, a Blob store holds the nightly backups (`backups/`). |
| `BACKUP_KEY` | production | **Exactly 43** random letters and digits (that is 32 bytes in base64): encrypts the nightly backups. Keep a copy **outside Vercel** (the password manager): without it no backup can be opened. Never change it, or older backups stay locked to the old key. |
| `LX_SIGN_KEY` | production | **Exactly 43** random letters and digits (32 bytes in base64), like `BACKUP_KEY` but a different one: the key that signs the Z, month and year closures (CPT-01a, [security](security.md#signed-closures-and-the-technical-log)). Without it a key is generated and kept with the data, and the owner's warnings say so (Réglages › Données › Système; Mise en route lists it from WP-10). The demo ignores it and keeps its own public key. Keep a copy **outside Vercel**. Changing it is recorded in the technical log; closures older than 36 h that were never signed are then signed « en retard », nothing else is re-signed. |
| `PUBLIC_URL` | at the switch | `https://barberlarchitecte.com`: used in SMS links and payment return URLs. Defaults to the Vercel production URL (the provisional address), which is right **until the domain points at Vercel**: set before that, links would open the old WordPress site. Set it on the switch day, right after the DNS change, in the same redeploy as `SMS_PROVIDER`, so no text ever leaves with a wrong link. |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | for online payments | Without them (or without the webhook secret), production asks no deposit online and the till's QR code is off; the demo uses the test checkout page. With Stripe, an unpaid booking holds its slot at least 31 minutes, the lifetime of a Stripe checkout. `STRIPE_WEBHOOK_SECRET` may hold several signing secrets separated by commas (a secret being rolled, the test and the live endpoint): a notice signed with any of them is accepted. See [Stripe](#stripe-webhook-refunds-disputes-payouts). |
| `SMS_PROVIDER` | for real SMS | `brevo` (with `BREVO_API_KEY`, `SMS_SENDER` ≤ 11 characters, e.g. `LArchitecte`), `gateway` (the salon's own phone, with `SMSGATE_USERNAME` and `SMSGATE_PASSWORD`, see [SMS routes](#sms-routes-brevo-the-salons-phone-whatsapp)) or `twilio` (with `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM`). Without it, messages wait in the outbox (Relances › Messages envoyés, « attend un fournisseur »); once a provider is set, those more than 6 h late or whose appointment has started are marked « trop tard » instead of leaving. **Set it only on the switch day, after the DNS change**: from the first WordPress import, the new salon queues the evening-before reminders of the imported bookings, which WordPress still sends itself until then. |
| `SMSGATE_USERNAME`, `SMSGATE_PASSWORD`, `SMSGATE_URL` | for the salon's phone | The credentials SMS Gateway for Android shows on its Home tab (cloud server), type Sensitive. `SMSGATE_URL` only for a private server of the app (default `https://api.sms-gate.app/3rdparty/v1`). May be set before `SMS_PROVIDER=gateway`: Réglages › Messages › Canal d’envoi can test the phone first. |
| `WHATSAPP_SENDER` | for WhatsApp | The salon's WhatsApp Business number in international format (`+33…`), connected to Brevo; with `BREVO_API_KEY`. WhatsApp then leaves first for the texts that have an approved template (Réglages › Messages › Canal d’envoi), SMS stays the fallback. |
| `EMAIL_FROM`, `EMAIL_REPLY_TO` | for e-mails | With `BREVO_API_KEY`, e-mails leave through Brevo: the client's confirmation with the calendar file (`.ics`) and cancellation (Réglages › Messages › E-mails aux clients), the owner's alerts, evening summary (with the Z and its seal) and Monday report (Réglages › Messages › Me prévenir). `EMAIL_FROM` is a sender verified in Brevo, with the domain's DKIM and SPF set (e.g. `Barber L’Architecte <rdv@barberlarchitecte.com>`); replies go to `EMAIL_REPLY_TO` (the salon's inbox). Without them, e-mails wait in the outbox like SMS (Relances › Messages envoyés, « attend un fournisseur »). A wrong key shows « Clé Brevo refusée » on each mail. The evening summary and the Monday report leave on a tick after their time: on Vercel without Pro crons, they need the external cron of step 10. Like `SMS_PROVIDER`, set on the switch day only. |
| `LX_INDEX` | at go-live | `1` lets search engines index the public site: the build removes its noindex and opens `robots.txt` (the Comptoir, client links, the API and `/demo` stay out). Unset, nothing is indexed. Takes effect on the next deploy. |
| `CRON_SECRET` | production | 64 random letters and digits. Enables `/api/cron/tick` for the external scheduler (**required**, see below) and derives the key of the SMS provider's STOP webhook. |
| `LX_DATA_FILE`, `LX_FAKE_NOW`, `LX_INSECURE_COOKIES` | development only | Local journal file; a fixed clock (ignored in production); cookies over plain http (ignored by a production deployment on Vercel). |

The Comptoir shows what is missing: Réglages › Mise en route ticks each step live, and Réglages › Données › Santé lists the scheduler, Stripe's last webhook, failed or waiting messages, the last backup, the journal's integrity, the public address and indexing (`GET /api/v1/health`, owner only).

## Going live (checklist)

The provider's technical reference. The owner's version, day by day, is the next section.

1. **Database**: add Neon Postgres from the Vercel marketplace (region Frankfurt or Paris). It sets `DATABASE_URL`.
2. **Secrets**: `LX_MODE=production`, `SESSION_SECRET`, `SETUP_TOKEN`, `BACKUP_KEY`, `LX_SIGN_KEY`, `CRON_SECRET`, created in Vercel's screen as above (`PUBLIC_URL` waits for the switch, item 11). Add a Vercel Blob store too, created with **Private** access (Vercel fixes it at creation; a public store refuses the backups), for the nightly backups: it sets `BLOB_READ_WRITE_TOKEN`. In production it is required: without it there is no automatic backup, the download is sealed in one response (Vercel caps those at 4.5 MB, about 30 000 operations, some 16 months of a busy salon) and a file over 2.5 MB cannot be uploaded for a restore.
3. **Deploy**, open `/comptoir`: the setup screen asks for the installation code (`SETUP_TOKEN`), the owner's name, e-mail, password and PIN. Then remove `SETUP_TOKEN` and redeploy.
4. **Salon**: Réglages › Le salon (legal name, SIRET, VAT number for the tickets), Horaires (weekly hours, public holidays in one tap), Réservation (notice, cancellation delay, deposits), Messages.
5. **Team**: Équipe › Ajouter, one per person, with their PIN; set each barber's hours, services and commission. Until the first chair exists, the Agenda says « Ajoute ton équipe pour ouvrir l’agenda ».
6. **Catalogue**: services (price, length, online or not, deposit), products with stock. « Reprendre la carte de l’ancien site » takes over the WordPress menu in one tap.
7. **Devices**: on the salon tablet, sign in as the owner, Réglages › Appareils › Enregistrer ce poste. The team signs in there with their PIN.
8. **Stripe** (deposits, QR payments): create the account, add `STRIPE_SECRET_KEY`; add a webhook endpoint `https://<domain>/api/pay/stripe/webhook` with the events listed in [Stripe](#stripe-webhook-refunds-disputes-payouts) (Réglages › Paiements shows them in one block to copy), copy its signing secret into `STRIPE_WEBHOOK_SECRET`, and keep Stripe's automatic daily payouts. Test with Stripe's test keys first, then switch to live keys **and a live webhook** (live mode has its own endpoint and its own signing secret) before opening bookings: with test keys (`sk_test_`) in production, a test card confirms a booking and the till deducts its deposit although no money moved (the Comptoir warns « Stripe en mode test »). The day Stripe goes live, the deposit rule appears in the CGV: save Réglages › Réservation once that day, which dates a new CGV version (`cgvVersionOf`, server/settings/shop.js). The no-show fee clause stays off the CGV: it shows only when `/api/public/salon` says `payments.cardOnFile === true`, and nothing keeps cards yet.
9. **SMS**: Brevo account (French, pay as you go), sender name approved. `BREVO_API_KEY` and `SMS_SENDER` may be stored early; `SMS_PROVIDER=brevo` is set **on the switch day, after the DNS change**, with `PUBLIC_URL` (item 11): between the first WordPress import and the switch the new salon must send no text (the imported clients would get a second reminder, with a link to the old site). Texts queued meanwhile wait, and those more than 6 h late are expired instead of sent. Réglages › Mise en route › SMS › « Envoie-moi un SMS test » then sends one text to the owner's French mobile through the real provider (three an hour at most). To confirm with Brevo before go-live: the STOP number used in the STOP mention (default ` STOP au 36173`, Réglages › Messages), the fields of its webhook's payload (STOP replies arrive at `POST /api/sms/webhook`, see [security](security.md#public-endpoints)), and the sender name. The owner decides the countries texts may go to (Réglages › Messages; Monaco +377 is not in the default list).
10. **Scheduler (required)**: a free cron (cron-job.org) calling `GET https://<domain>/api/cron/tick` every 5 minutes (**every minute** when texts leave from the salon's phone, `SMS_PROVIDER=gateway`: see [SMS routes](#sms-routes-brevo-the-salons-phone-whatsapp)) with the header `Authorization: Bearer <CRON_SECRET>`. Texts held by quiet hours leave at 8 h only if something dispatches them, and a text more than 6 h late is expired instead of sent: without the cron, the morning's reminders wait for the first visit to the Comptoir or the site. Every visit to the Comptoir or the site ticks too, so « a tick ran » proves nothing: Mise en route ⑪ and Santé read the calls of `/api/cron/tick` this server has seen, and above all the messages themselves (shared by every instance): red when a text due in the last 24 h waited more than 30 minutes with no dispatch at all (the 08:00 texts held by quiet hours, typically), when one is waiting like that now, and « à vérifier » (not red: the calls are counted per instance, and cron-job.org may reach another one) when this server saw no cron call for 30 minutes during opening hours. A long relance draining 10 texts a tick is not late. The owner's evening summary and Monday report (Réglages › Messages › Me prévenir) also leave on a tick after their time: without the cron, an evening when nobody opens the Comptoir or the site skips the summary.
11. **Domain and indexing**: point the domain at Vercel (DNS table below). `/` already serves the site (the demo page is at `/demo` and sends production visitors to `/`). Then, in one redeploy: `PUBLIC_URL=https://barberlarchitecte.com`, `SMS_PROVIDER` (item 9), the e-mail sender, Stripe's live keys, and `LX_INDEX=1` so Google indexes the site, with `sitemap.xml` and the canonical address. Check every old address on the live domain with `node scripts/check-redirects.mjs https://barberlarchitecte.com` (the list of the end-to-end test). The build lists in `sitemap.xml` only the pages it has: `/formations`, `/carte-cadeau` and the legal pages join it when their packages ship, and until then the old WordPress links to them land on the 404 page.
12. **Old WordPress**: Réglages › Reprendre WordPress takes the bookings export (Salon › Calendrier, one CSV per year), optionally the WXR export, the plugin's client CSV and hand-made CSVs of paper gift cards and running carnets: client files (merged by phone or e-mail, no promotional SMS), past visits (they count for each client's rhythm, not for the chairs' figures, and never wait at the till), upcoming bookings (no SMS at import; each old barber with upcoming bookings must be matched to an active chair). On the cut-over day, export and drop the files again: only new bookings and what changed on the old site since are taken (cancelled, moved, taken place), unless the booking was already handled in the Comptoir, which is then listed for a look. Keep WordPress read-only for a month at `ancien.barberlarchitecte.com`. Its indexed addresses already redirect to the matching place on the site (`vercel.json`), and the cancel, pay and account links in clients' old e-mails land on `/ancien-lien`, which never acts on them and opens the imported appointment or asks for the client's number. Each run leaves a report (Réglages › Reprendre WordPress, kept on the server, so it is there after a reload; `GET /api/v1/import/runs`): rows of the export against what was made, already there, skipped by reason and left out, « Tout est compté ✓ » or « Écart de n », and a CSV to send to the provider (four `compte` lines first, with the figures of each type, then one line per row to look at). People with no visit for 3 years are not brought in (the retention rule), and a booking still to come that the export no longer lists, inside the period its CSV covers, is cancelled here without a text (nothing is cancelled when more than 5 and 20 % of them vanish at once). Imported files carry `marketingSrc: 'wordpress'`: never asked, no promotional consent.
13. **Monitoring**: UptimeRobot (free) on `https://<domain>/api/public/live` every 5 minutes, alerts to the owner's phone and to the provider.
14. **Fiscal**: Le Comptoir is a « caisse de gestion » (its Caisse page says so in production): until it is certified by an accredited body (see [security](security.md#fiscal-note-france)), keep the current certified till as the legal one, which prints the client's ticket.

## Mise en ligne : la liste du gérant

Quatre moments, chacun en deux colonnes : ce que tu fais toi-même (dans le Comptoir, sur ton téléphone, dans tes comptes), et ce que ton prestataire fait (Vercel, DNS, clés). Le jour J est un **lundi** : le salon est fermé, rien ne se perd si la bascule prend une heure. Dans le Comptoir, **Réglages › Mise en route** coche chaque étape toute seule, dans le même ordre ; une ligne rouge se regarde tout de suite.

Rien ici ne demande de modifier le code : tout se règle dans le Comptoir et dans les écrans de Vercel, IONOS, Stripe et Brevo. Une variable changée dans Vercel ne compte qu’après un redéploiement.

**Ta caisse certifiée reste la caisse légale, même après le jour J.** Le Comptoir est une « caisse de gestion » (sa page Caisse le rappelle) : chaque vente passe aussi sur ta caisse certifiée, qui imprime le ticket du client. Son Z est le Z fiscal ; les exports du Comptoir (ventes, TVA, Z, commissions) sont des chiffres de gestion, dis-le à ton comptable. Se servir du Comptoir comme seule caisse sans certificat expose à une amende de 7 500 €.

**Entre le premier passage de Reprendre WordPress (J-7) et la bascule du domaine (jour J), le nouveau salon n’envoie aucun SMS ni e-mail** : WordPress envoie encore ses propres rappels, et les liens du nouveau salon ouvriraient l’ancien site. Le fournisseur SMS, l’expéditeur des e-mails et l’adresse définitive (`PUBLIC_URL`) se branchent le jour J, juste après les DNS. Jusque-là, Mise en route ⑦ et ⑧ restent « à faire » : c’est voulu. Les messages préparés entre-temps attendent ; ceux de plus de 6 h ne partiront jamais.

#### Plan de retour

Si le site ne répond pas ou que les réservations échouent et que ce n’est pas réglé en une heure : le prestataire remet chez IONOS les valeurs notées à J-2 (`A` et `AAAA` de `@`, `CNAME` de `www`) ; avec le TTL à 300 s, l’ancien site revient en quelques minutes. Il remet aussi les deux adresses de WordPress à `https://barberlarchitecte.com` (et décoche la case d’indexation), puis retire `SMS_PROVIDER`, `EMAIL_FROM` et `PUBLIC_URL` du nouveau salon et redéploie : il n’envoie plus rien pendant que WordPress reprend la main. Tu rouvres les réservations et les rappels sur WordPress. Les rendez-vous pris entre-temps restent dans le Comptoir (Agenda) : saisis-les dans WordPress, puis on recommence la bascule un autre lundi.

## Stripe: webhook, refunds, disputes, payouts

One payment core serves every provider (`server/payments/provider.js`): each payment is refunded through the provider it was paid with, never through whichever is plugged in now. If that provider is gone (keys removed), the till answers « Ce paiement est passé par Stripe, qui n’est plus branché » : refund it from Stripe's dashboard, then make the credit note as « remboursé hors caisse ».

- **Endpoint**: `https://<domain>/api/pay/stripe/webhook`. The older `https://<domain>/api/stripe/webhook` stays an alias (same handler), so an endpoint declared before keeps working.
- **Events** (Réglages › Paiements, one block to copy): `checkout.session.completed`, `checkout.session.expired`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`, `payout.paid`, `payout.reconciliation_completed`. Memberships (PAY-03) add theirs to the same block.
- **Several secrets**: `STRIPE_WEBHOOK_SECRET=whsec_a,whsec_b` while a secret is rolled, or with a test and a live endpoint on the same deployment.
- **Answers**: a notice we refuse (unknown payment, an amount that differs) is logged and answered 200 `{ ignored }`, so Stripe stops sending it; a database or network failure answers 5xx and Stripe retries. Each object is handled once (a payment's status, the total refunded, a dispute's id, a payout's id): a notice sent twice changes nothing.
- **Refunds made in Stripe's dashboard** are recorded (`payment.refundedOutside`) and shown in Caisse (« Remboursé chez Stripe sans avoir : fais l’avoir », with the ticket). The credit note then moves no money again: the till sees that Stripe already gave it back. A deposit on no ticket refunded in full simply stops counting at the till. Our own refunds carry `metadata[lx]` at Stripe: when a `charge.refunded` says more than our records, Stripe is asked for the charge's refunds and ours count only once our records hold them, so our refund whose notice outruns our own write is never taken for a dashboard one. A `payment.refundedOutside` followed by its « remboursé hors caisse » credit note is one refund, not two.
- **Till refunds** are keyed at Stripe by the request: a replayed request gets its first answer and refunds nothing again. A refund Stripe refuses reads « Remboursement refusé par Stripe : … ».
- **A deposit whose visit will not happen** (cancelled, no-show), paid and on no ticket, shows in Caisse › À traiter with « Garder l’acompte » (a ticket « Acompte conservé » paid by it: revenue of the day) and « Rembourser » (through the provider; also the retry when a refund on cancellation failed).
- **Disputes** show at the top of Caisse with their answer date; « Copier le dossier » copies what the journal knows (booking, CGV accepted, texts sent, the visit, the ticket; no phone, no e-mail) to paste in Stripe › Litiges.
- **Automatic daily payouts** (Stripe › Settings › Payouts) are required for reconciliation: each payout lists its balance transactions, and **Stripe fees are recorded at each payout**, per payment (Réglages › Paiements › « Voir les paiements et virements », or the button of Caisse's « En ligne » block when it shows). Stripe lists a payout's transactions only once it has reconciled it: a `payout.paid` still `reconciliation_status: in_progress` is answered `{ ignored: 'reconciling' }` and recorded on `payout.reconciliation_completed`. A payout of more than 500 lines is recorded `truncated: true`. A payout's arrival date is the bank date to match. Stripe's fees are invoiced from Ireland: the accountant self-assesses their VAT.
- Stripe's own error texts never reach a client: a refused card reads « Paiement refusé par ta banque », anything else « Paiement en ligne indisponible ». The staff see Stripe's words on a refused refund; the logs (`[lx] stripe`) always have them.

## SMS routes: Brevo, the salon's phone, WhatsApp

Every automatic text (confirmation, reminders, review, relances, place libérée, cancellations, gift card codes…) goes through one route, chosen in Vercel and checked in Réglages › Messages › **Canal d’envoi**: the route in use, whether each one is configured (never a key shown), « Envoyer un test » to the owner's phone per route, and the WhatsApp templates. Quiet hours and consent rules are the same whatever the route. In the demo nothing leaves; the outbox (Relances › Messages envoyés) shows the route each text would have taken.

**Who gets what** (FID-01, one rule per class of text, `classOf` in server/core/templates.js; the same rule when the text is queued and again as it leaves):

| Class | Texts | Needs | Route |
|---|---|---|---|
| service | confirmation, reminders, cancellation, receipt, place libérée, gift card codes, lookup links | the client takes texts (« SMS de confirmation et de rappel » on his file, the booking's switch) | SMS or WhatsApp |
| relation | the Google review request | texts on, no STOP, a file that is not erased; an e-mail only to a file without a phone | SMS only (never WhatsApp) or that e-mail |
| marketing | relances, offers | the client's yes to offers, the STOP mention, the quiet hours | SMS only |

A client imported from WordPress was never told about the new site: he gets no relation or marketing text until the first service text sent to him (his next reminder, typically) has left with one more line, « Nouveau site du salon. Tes données : https://<site>/confidentialite », or until he changes his consent himself (the site's box, a STOP; the owner's switch at the counter does not count). That line makes his first text one SMS longer (a confirmation then takes two), once per imported client. A sign-in code never carries it (its words are filled as it leaves): the next service text does. When the salon's phone reports later that this very text failed after all (`sms:failed`), the file counts as never told again and the next service text carries the line. A contract's acknowledgement (`legal`: the membership texts to come) is never « trop tard » and is tried again until it leaves; a text the client asked for himself (`requested`: the lookup links, the sign-in codes to come) leaves before everything else.

**Order and pace**: each dispatch sends what the client is waiting for first (codes, links he asked for), then the service texts, then the review requests, then the offers; within each, the oldest first. A relance of 200 texts never holds back a reminder.

| Route | Cost | What to know |
|---|---|---|
| **Brevo SMS** (`SMS_PROVIDER=brevo`) | about 0,045 € HT per SMS in France (pay as you go; check Brevo's current grid), one text = 160 GSM characters | Sender name « LArchitecte »: clients cannot answer it. Offers end with « STOP au 36173 » (Brevo's STOP number, to confirm with Brevo). |
| **Téléphone du salon** (`SMS_PROVIDER=gateway`) | the phone plan only (a SIM with unlimited SMS, a few euros a month) | Texts leave from the salon's real number and clients can answer it: answers land in Relances › Demandes (« Réponse SMS »), a STOP takes the client off the offers, whose mention becomes « STOP : réponds STOP ». Use a **spare Android phone with its own SIM**, kept at the salon, **plugged in and on Wi-Fi**, battery optimisation off for the app. Operators' fair-use terms can forbid heavy automated sending: a 4-chair salon sends a few dozen texts a day, but keep the SIM dedicated to it. The server never hands the phone more than 5 texts per dispatch, one every 3 s: **set the cron to every minute** (cron-job.org allows it), about 300 texts an hour; with a call every 5 minutes it is 60 an hour, and texts more than 6 h late expire (« trop tard »). Santé says « règle le cron toutes les minutes » when the calls it sees are more than 3 minutes apart; it is only a hint (each server instance sees its own calls) unless texts are also waiting or left late, then the line turns red. If the phone is off, texts wait in the app's queue and leave when it is back. With `BREVO_API_KEY` set too, a service text the phone's server refuses (wrong credentials, phone unreachable) goes once more through Brevo SMS, from « LArchitecte » (outbox: « par Brevo, en secours »), but not after a timeout (the phone's server may have taken it already: the text stays failed rather than reach the client twice); offers and review requests do not: they leave from the salon's number or not at all. |
| **WhatsApp + SMS en secours** (`WHATSAPP_SENDER`) | Meta's price per message, by category (France, roughly 0,03 € Utility and 0,07 € Marketing; check Brevo's grid) | Needs the business verified by Meta and **one template approved by Meta per message** (Brevo › WhatsApp › Modèles): Utility for confirmations, reminders, cancellations, receipts, gift cards. **Service texts only**: the review request and the relances would be Marketing there, and need the client's own yes to WhatsApp (CNIL: a separate opt-in per channel), which the salon does not collect, so they always leave by SMS; Canal d’envoi shows them « SMS uniquement » and the settings refuse a template for them. With Meta's **coexistence**, the salon keeps its WhatsApp Business app on the same number. A text whose template is not mapped, a relance written by hand, or a text WhatsApp refuses (number not on WhatsApp, template rejected) leaves by SMS instead, in the same minute and once; the outbox notes « Par SMS : » and why. |

**Never automate WhatsApp Web** (browser robots, unofficial libraries): it breaks WhatsApp's terms and gets the salon's number banned. Only Brevo's official API is used.

**Setting up the salon's phone** (provider, 20 minutes):
1. On the Android phone, install « SMS Gateway for Android » (sms-gate.app, open source; from its GitHub releases or the Play Store), open it, switch on **Cloud server**, and note the username and password shown on its Home tab.
2. In Vercel: `SMSGATE_USERNAME`, `SMSGATE_PASSWORD` (Sensitive), redeploy. Réglages › Messages › Canal d’envoi › Téléphone du salon › « Envoyer un test »: the text arrives on the owner's phone from the salon's number.
3. Register the webhook once, so answers, STOP and delivery reports come back (the address is in Réglages › Messages › Bons plans et STOP; it needs `CRON_SECRET`):
   ```
   for e in sms:received sms:delivered sms:failed; do
     curl -X POST -u "$SMSGATE_USERNAME:$SMSGATE_PASSWORD" -H 'Content-Type: application/json' \
       -d '{"url":"https://barberlarchitecte.com/api/sms/webhook?k=<la clé>","event":"'$e'"}' https://api.sms-gate.app/3rdparty/v1/webhooks
   done
   ```
   A client's answer is then a request in Relances › Demandes, answerable by SMS, with the text it answers (« Réponse à : Demande d’avis du 3 nov. », the last text sent to that number in the 7 days before). A mere « ok », « merci », « d’accord », an emoji or two characters answered to a review request, a reminder or a receipt is filed by itself under « Traitées » (no badge); anything else stays « à traiter ».
4. On the switch day, `SMS_PROVIDER=gateway` instead of `brevo` (same rule: after the DNS change).

**Setting up WhatsApp**: connect the salon's WhatsApp Business number in Brevo (WhatsApp › Paramètres; with coexistence the app keeps working), have the business verified by Meta, create one template per message in Brevo and submit it. Put `WHATSAPP_SENDER` in Vercel and redeploy. Then in Canal d’envoi, for each approved template: its number in Brevo and its variables in order (for « Salut {{1}}, rendez-vous {{2}} à {{3}} » : `prenom, date, heure`). Brevo does not document how it names a template's variables in its API: each value is sent under its position (`params.1`, `params.2`…) and its name (`params.prenom`); « Envoyer un test » on WhatsApp checks it on the real template before switching « Envoyer par WhatsApp » on.

## Day to day

- Morning: the agenda is ready; walk-ins go in the queue (Agenda › Passage, key P), the site shows the live wait.
- At the till: open the drawer with the float, check out each client (the deposit and subscription are already on the ticket), propose the next appointment on the confirmation screen. Each sale is also rung up on the salon's certified till, which prints the client's legal ticket: Le Comptoir is a « caisse de gestion » (see [security](security.md#fiscal-note-france)).
- Evening: Caisse & clôture › count the drawer by denomination, then close the day (Z). A closed day cannot change; mistakes are fixed the next day with a credit note.
- Weekly: Relances (clients past their rhythm), Rapports (heat map, team), stock alerts in the feed.
- Monthly: the month closes by itself on the 1st after 05:00 (Caisse & clôture › Clôtures mensuelles), once every day of it has its Z: a drawer left uncounted holds it back, and the Comptoir says which day. « Clôturer octobre » does it sooner. Then Rapports › Exports (sales, VAT and Z, commissions) for the accountant, as management figures: the certified till's Z is the fiscal one.

## Abonnements (PAY-02)

Two products, two words: the **abonnement** is the monthly membership, the **carnet** the prepaid pack sold at the till (« Carnet 5 coupes »; its data keeps the name `pack`).

- **Settings**: `membership { enabled, plans (4 at most), graceDays }`, owner only. Off in production until a lawyer has read the membership CGV (Mise en route › Nouveautés: « Abonnements : en attente de la relecture des CGV »); on in the demo with Essentiel (34 €, 2 coupes classiques a month) and Illimité (49 €, one cut every 7 days, coupe classique or coupe + contour). A plan: `cuts` per billing month (0 = illimité), `minDays` between two covered cuts (7 by default for illimité), the services it covers. A member keeps what he signed for: changing a plan's price moves nobody. No pause, no SEPA, no plan change in v1.
- **The rule**: a member's cuts exist only inside a paid period (`member.renewed`), salon days `[start, end)`. Two tolerances: the renewal day itself (the provider's webhook may come late) and, after a refused renewal, `graceDays` (7) while the provider retries. A cancellation takes effect at the end of the paid period (or at once when nothing is paid for today); the 14-day withdrawal refunds the first month less the cuts taken (Essentiel, one cut: 17 €).
- **Money**: each paid month is a numbered ticket of one `membership` line at the plan's VAT, paid online (payment kind `membership`), no barber, revenue on the day it is collected; paid after the Z, it opens the next day's till. A member's cut is a 0 € service line that keeps its `listPrice` and carries `credit` = price ÷ cuts (÷ 4 for illimité), the barber's commission base. A withdrawal's refund is an ordinary credit note on the month's ticket.
- **Texts**: memberWelcome, memberCancelled (memberStopped when it ends the same day) and memberWithdrawn (memberWithdrawnNone when the cuts taken are worth the month) also leave by e-mail (the acknowledgement on a durable medium: the day received, the day it takes effect, what stays included) and are `legal` (never expired nor held: FID-01's dispatch reads the flag, so FID-01 merges first); memberFailed or memberAction once per refused invoice; memberEnded when retries are exhausted on a contract that was paid. `{lien}` is the member's page (PAY-03's `memberLink`); until it exists the texts carry no link rather than a dead one. The owner gets an e-mail for a client's cancellation (here or in Stripe's portal) or withdrawal and for an end for want of payment.
- **Reading a member**: `statusIn(s, m, day)`, `periodIn`, `liveIn` (domain/membership.js) apply the salon's `graceDays`; the screens and the till use them so they never disagree. A cut's receipt line names its billing month (« Abonnement · coupe 2/2 (26/09–25/10) »), « hors forfait » when forced. Rapports count the months under the category « Abonnements », in no barber's row.
- **The demo** renews by itself (`server/commands/steps/sim-billing.js`, demo salon and simulated members only): a period that is over is paid on the next tick (invoice `sim_<id>_<n>`, one ticket per tick), a member flagged `demoFail` is refused once and pays two days later, a cancellation that took effect ends the member. Sixteen members are seeded: 12 running, 1 in grace, 1 ending, 2 cancelled.
- A client file with a running membership cannot be erased: cancel it first (« Résilier tout de suite »).

### Abonnements chez Stripe (PAY-03)

Each month is billed by **Stripe Billing**: Smart Retries, the dunning e-mails and the hosted card page cost about **0,7 %** of what it bills on top of the card fee, less than building and running our own retry engine on a traffic-carried tick. Stripe's fees are invoiced from Ireland: reverse-charge VAT (autoliquidation), see Réglages › Comptabilité.

**To set once in Stripe** (Dashboard › Settings › Billing):
- **Subscriptions and e-mails › Manage failed payments**: Smart Retries, **8 tries within 2 weeks**, then **cancel the subscription** (the end for want of payment then reaches us as `customer.subscription.deleted`, the member ends « faute de paiement » with his text and the owner's e-mail).
- **Customer e-mails**: « failed payment » and « 3-D Secure / action required » **on**, their link pointing to the salon's page (the hosted invoice page is fine); **card expiring** reminders **on**; **trial ending** reminders **off** (a start in 14 days is not a trial in our words, and the client already got its date by e-mail).
- **Customer portal**: payment method update and invoice history **on**, **cancellation off**: the salon's own « Résilier » sends the legal acknowledgement (date received, date it takes effect). A cancellation made in the portal anyway is still caught (`customer.subscription.updated`) and acknowledged the same way.
- **SEPA** stays off in v1: it needs Stripe's extra verification and the salon's own creditor ID before the first debit.
- **Webhook**: add `invoice.paid, invoice.payment_failed, invoice.payment_action_required, customer.subscription.updated, customer.subscription.deleted` to the endpoint's events (Réglages › Paiements lists them in the same block). Nothing else of Billing is needed: `invoice.created` is answered at once (Stripe holds an invoice up to 72 h while that notice fails).

**How it runs** (server/http/routes-membership.js, server/payments/billing.js):
- The site's « Je m'abonne » opens Stripe Checkout (mode subscription) for the plan's Price, found at Stripe by its key `lx_<planId>_<cents>` or created once (nothing stored on our side; a new price makes a new Price, members keep theirs). Unticked « commencer tout de suite »: nothing is charged before day 15 (`trial_end`, the day after the 14 days of withdrawal); the client gets the contract's confirmation by e-mail when the checkout is done (start date, the 14-day withdrawal, the CGV version accepted), the welcome text with the first payment. Stripe's page would word that start as a free trial: our line above its button (`custom_text[submit][message]`) says « Ton abonnement commence le … : rien n'est prélevé avant », since cuts are at the normal price until then.
- Every billing notice is **re-read from Stripe** before anything is written (the invoice, the subscription), so a notice seen twice, late or in the wrong order changes nothing more: one activation, one ticket per paid month. The member is found by its subscription or by our id in its metadata.
- A renewal refused: grace (`graceDays`) and one text with the member's page; paid on a retry, back to normal. Money Stripe takes when no contract covers it (a cancellation Stripe never heard of, a second subscription of the same client) is **given back at once** and that subscription stopped; the owner gets an e-mail.
- The member's page (`/abo/<lien>`, PAY-04's screen) works under a signed link that **expires**: 7 days in the salon's texts, 1 hour when asked from /resilier. There: cancel (end of the paid month, or today when nothing is paid for today), withdraw within 14 days (the month less the cuts taken, refunded on the month's ticket with its credit note A…), change the card (Stripe's page).
- /resilier without the link: a number or an e-mail sends it to the phone **and** the address on file (3 a day per file, with the other « send me a link » texts). Neither at hand: first name and the subscription's e-mail record a cancellation received now but **to confirm**: the owner gets « Résiliation à confirmer · Karim », and « Résilier » on the client's file confirms it and stops it at Stripe at the end of the paid month (a start in 14 days not begun yet is called off at once and acknowledged; the confirmation deletes it at Stripe). The salon cannot decline it: it takes effect like any cancellation (a renewal Stripe charges after it is refunded), the confirmation only tells Stripe sooner; whoever doubts it calls the client. To check with the salon's lawyer. Unmatched requests e-mail the owner at most 5 a day (counted in the journal).
- A **dispute** on a month: Stripe stops billing (the invoices to come are voided), the member's cuts are no longer covered, the owner gets « Litige sur l'abonnement de Karim : résilier ? »; lost, « fais l'avoir du mois contesté » with the ticket, and the contract **stays held** (no charge, no covered cut, counted `disputed` in the figures, not among the payments in trouble) until the owner cancels it (« Résilier tout de suite »), after which the file can be erased or offered a new membership; won, billing goes on. Every other dispute e-mails the owner with its answer date, and a refund made in Stripe's dashboard « fais l'avoir ».
- Clients › Abonnés (`GET /api/v1/memberships`) catches up by itself, at most 5 members a visit, those whose month ended more than a day ago with no renewal recorded; « Relire Stripe » (`POST /api/v1/memberships/:id/sync`) does it for one.
- A **withdrawal** from the member's page refunds by itself (the month less the cuts taken, credit note A… on the month's ticket); the owner's e-mail says « Remboursé automatiquement … », or, when Stripe refused, « Remboursement automatique en échec : rembourse depuis Caisse » (within 14 days, the law's). A credit note refused after the money moved (the day's Z done) shows in Caisse as « remboursé hors caisse » once, never twice.
- An **offer from the counter** needs the client's number and e-mail on the file (the contract's confirmation goes there), one at a time per file; the SMS needs `member.manage` (the owner), the QR code only `client.edit`.
- The demo: the test page shows « Abonnement Essentiel · 34 €/mois »; its confirmation pays the first month (invoice `sim_<id>_0`) and the demo's billing renews it; a start in 14 days is « Confirmer mon abonnement »: its confirmation e-mail leaves, and the demo's billing pays its first month on the start day; « Changer de carte » says « Démo : la carte est à jour. »

## Google reviews

- **When**: once a visit is done and its ticket paid (the later of the two), after the delay of Réglages › Messages › Avis Google (2 h by default), checked by the tick (`server/commands/reviews.js`). Inside the quiet hours (20 h to 8 h, Sundays, public holidays) it waits for the end of them: a visit paid at 19:30 is asked at 8:00 the next morning, a Saturday evening one on Monday at 8:00. A request that could not leave within 24 h of that time (no traffic and no cron for a day) is dropped rather than sent days late.
- **Who**: once per client per quarter **of the visit** (a visit of 31 March asked on 1 April counts in the first quarter), whatever the number of visits. Never after a no-show, a cancellation, a ticket refunded (even in part), a past visit imported from WordPress, nor to an erased file. It is a « relation » text (legitimate interest: a client who came, about his visit): **a STOP stops it**, like an offer, also when it was already waiting for the morning. By SMS, never WhatsApp, when the client takes texts; a client who switched texts off gets nothing (he said no: no e-mail behind his back). By e-mail only to a file without a phone, when e-mails are on (the link as a button), ending with « Tu ne veux plus de demande d’avis ? Réponds « stop » à ce mail ou dis-le au salon. »: the answer reaches `EMAIL_REPLY_TO`; until the one-tap link (FID-04), take the e-mail off his file. Not to a file imported from WordPress before it was told about the new site (above).
- **No review gating**: every eligible client gets the same text. There is no « tu as aimé ? » question, no private form for unhappy clients and no reward: Google's policy forbids asking only satisfied customers, and French consumer law forbids filtering or rewarding reviews (Code de la consommation L111-7-2 and L121-1, décret 2017-1436). Do not add one.
- **The link**: the text carries `https://<site>/avis/<token>` (signed with `SESSION_SECRET`, kind `review`, the message's id), not the Google address itself: `/avis/:token` (vercel.json → the function, `noindex`) records `review.clicked` with the message id only (no address, no device, no person in the chain), once per message, then redirects (302) to `shop.reviewUrl`. A forged or broken token, and link previews (WhatsApp, iMessage, crawlers), are sent to Google without being counted; with no Google link set, to the site. Changing `SESSION_SECRET` breaks the links already sent the same way: they then go to Google uncounted.
- **The Google link** lives in Réglages › Messages › Avis Google (no longer in Le salon): the owner copies it from Google Business Profile › Demander des avis › copier le lien (`g.page/r/…/review`); `search.google.com/local/writereview?placeid=…` and `maps.app.goo.gl/…` are accepted too. Mise en route says when it is missing or opens something else than the review form (the profile, the map). « Tester le lien » opens it; « Envoyer un test » sends the real text, with a tracked link of its own, to the owner's mobile (or e-mail), three per hour, never counted in the figures.
- **Length**: the default text (« Merci {prenom} ! Ton avis Google nous aide énormément : {avis} ») stays in one SMS with the tracked link on the salon's domain. A text the owner saved before (the older, longer default) makes two: the Avis Google card says so and offers « Reprendre le texte conseillé ».
- **What the owner sees**: Rapports › Avis Google for the period (requests that left, links opened and their rate, by barber); the client file's line « Avis Google demandé le 12 oct. · ouvert »; each request in Relances › Envoyés. The reviews themselves are read on Google.
- **The demo** seeds its history the same way (requests for the seeded visits, about a third opened), so the card is never empty there.

## Backups and archives

- **Nightly backup** (`server/core/backup.js`): after 03:00 Paris, the scheduler seals the whole journal, personal data and credentials included, gzips it and encrypts it with `BACKUP_KEY` (AES-256-GCM), then writes a private Blob file `backups/YYYY-MM-DD.json.gz.enc`. It keeps the last 30 days and the first backup of each of the last 12 months. It needs `BLOB_READ_WRITE_TOKEN` and `BACKUP_KEY`, and some traffic or the external cron after 03:00. Only a production salon writes backups (never the demo, nor a Vercel preview, even with the same Blob token), and each file carries its salon's identity (the hash of the journal's first event), so another deployment's files are never taken for this salon's. A backup taken before a client was erased still holds that client until it ages out (a year at most); one taken after holds none of their personal data.
- Réglages › Données › Sauvegardes: « Dernière sauvegarde : cette nuit 03:02 ✓ », in red when it is older than 36 h or when `BACKUP_KEY` or Blob is missing. « Télécharger la sauvegarde chiffrée » (keep one off Vercel each month), « Sauvegarder maintenant ».
- **Restore**: a new deployment with an empty database, the same `BACKUP_KEY`, a `SETUP_TOKEN` and the old Blob store (or the downloaded file). For a drill, never give the drill deployment the salon's Blob store: it would be a production salon with the same identity, and its nightly backups would replace the real ones. Use the downloaded file, and give the drill none of the salon's SMS, e-mail, Stripe, cron, `PUBLIC_URL` or `LX_INDEX` settings: a restored copy with a provider would text tomorrow's reminders to the real clients. A file over 2.5 MB needs a fresh private Blob store of the drill's own. On the setup screen, « Installer depuis une sauvegarde »: pick a backup from Blob or upload the file (in one request up to 2.5 MB; a larger file goes in 2.5 MB parts and then needs the Blob store). The chain is verified before anything is written, and the journal then records « Salon restauré » with the file it came from; the team signs in with their usual passwords and PINs. Refused once the salon has any data. Reuse the same `SESSION_SECRET` and `PUBLIC_URL`, or every link clients already received by SMS (manage links, receipts, offers) stops working, and the same `LX_SIGN_KEY`: with another key (or none, the key kept with the data stays in the old database) the technical log records a new key, and closures older than 36 h left unsigned in the backup are signed with it « en retard ». **Everything after the backup's time is lost** (bookings, tickets, Z closures): and a client erased since then comes back, so do those erasures again (Clients › the client › « Effacer (RGPD) »).
- The fiscal archive: Réglages › Données › "Archive complète du journal" (JSON, without personal data, so it cannot restore the salon), verifiable offline. Keep one per month, and one per year for 6 years (fiscal archiving).
- Postgres providers keep their own point-in-time history, short on free plans (Neon: hours, not days; check the plan): not a backup to count on.
- Client file export (CSV) from the same screen.
- **Photos left from the old site editor**: while the Comptoir had « Le site » (removed), photos the owner uploaded or copied from WordPress, barbers' portraits among them (personal data), went to the Blob store under `site/` (or a `media/` folder next to `LX_DATA_FILE`). Nothing reads, serves or deletes them any more: if that salon ever used it, delete the `site/` prefix in Vercel's Blob screen (never `backups/`) and that `media/` folder.

## Incidents

| Symptom | Where to look | What to do |
|---|---|---|
| "Pas de connexion" on the Comptoir | the network | Writes are idempotent: retrying never doubles a sale. |
| A client says the slot was free but booking failed | nothing wrong | Someone took it first; the site keeps their choices and shows the next slots. |
| SMS or e-mails not leaving | Relances › Messages envoyés (channel, status and error), Réglages › Données › Santé (« Envoi des SMS », last failure) | Check `SMS_PROVIDER` and the provider's credit, or `BREVO_API_KEY` and `EMAIL_FROM` (a sender validated in Brevo); failed messages show the provider's reason. Salon's phone: is it on, charged, on Wi-Fi, the app running (« identifiants refusés »: `SMSGATE_*` changed in the app)? Canal d’envoi › « Envoyer un test » tells which route works. |
| Deposits stay "Acompte en attente" | Stripe dashboard › webhooks (Réglages › Données › Santé: « dernier webhook ») | The webhook secret or URL is wrong (`/api/pay/stripe/webhook`, or the older `/api/stripe/webhook`); unpaid deposits free the slot anyway once the wait is over (31 minutes with Stripe). A deposit paid after that is kept only if the slot is still free; otherwise the booking is cancelled and the deposit refunded. |
| "Anomalie" in Réglages › Données | the activity log, the database | The journal no longer verifies: stop, export the archive, contact the operator. Nothing in the app can produce this; only a direct database edit can. |
| Backup line in red (Réglages › Données) | the message under it, Vercel logs (`[lx] backup`) | Missing `BACKUP_KEY` or Blob store: add it and redeploy. Blob down: it retries every 15 minutes; « Sauvegarder maintenant » once it is back. |
| Planificateur in red (Mise en route, Santé) | cron-job.org's history for `/api/cron/tick` | The task stopped or its `CRON_SECRET` header is wrong (it answers 401): fix it there. Morning texts more than 6 h late are expired, not sent. |
| Red strip « Connexion à la base perdue · lecture seule » on the Comptoir | Vercel logs (`[lx] store unreachable`, `[lx] store append failed`, `[lx] boot`), the database provider's status page | The database does not answer. For 10 minutes each server answers reads from its memory (agenda, clients, the site's menu); a write answered « rien n’est enregistré » saved nothing, so that ticket goes on paper and is typed in once the strip is gone. A ticket answered « ce n’est peut-être pas enregistré » stays open in the till, not on paper: once the strip is gone, Encaisser again, it is never counted twice. After 10 minutes every page answers « La base de données ne répond pas », and the site « Le salon ne répond pas ». The strip leaves by itself within seconds of the database coming back; a Comptoir opened during the outage shows « Le Comptoir est injoignable » instead: tap Réessayer once the database is back. A strip that flashes only on writes while reads work (`[lx] store append failed` alone) is a database that reads but refuses writes (read-only after a failover, full disk, quota): the provider's side, not the network. |
| The site is down (UptimeRobot alert) | Vercel › Deployments, the status page | Roll back to the previous deployment (Vercel › Deployments › ⋯ › Promote); a DNS problem: the plan de retour above. |
| A barber's phone is lost | Réglages › Appareils, Équipe › Déconnecter partout | Revoke the device and the sessions; change the PIN. |

Logs: Vercel › Project › Logs (`[lx]` prefix for the app's own messages).
