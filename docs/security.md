# Security

## Who can do what

Four roles, each a set of capabilities (`server/domain/permissions.js`). Every write and every read of sensitive data checks the capability **on the server**; the Comptoir only hides what you cannot use.

| | Owner | Manager | Front desk | Barber |
|---|---|---|---|---|
| Agenda of every chair | ✓ | ✓ | ✓ | setting |
| Check out, see all sales | ✓ | ✓ | ✓ | check out: setting |
| Refunds, Z closure | ✓ | ✓ | | |
| Full phone numbers, client export | ✓ | ✓ | numbers | |
| Salon figures, month goal, sales and VAT exports (`report.shop`) | ✓ | ✓ | | never (own figures always) |
| Each barber's figures without commissions or tips (`report.team`) | ✓ | ✓ | | setting |
| The accountant's files: entries, VAT, month-end balances (`compta`, CPT-03; no client name in them; a manager gets the files in Réglages › Comptabilité, its configuration stays the owner's `settings`) | ✓ | ✓ | | |
| Text one's own regulars (`client.rebook`) | ✓ | ✓ | ✓ | setting (off in production) |
| Team, catalogue | ✓ | ✓ | | |
| Settings, devices, data, GDPR erasure | ✓ | | | |

The owner adjusts the barbers' toggles in Réglages › Équipe et accès; the matrix shown there is computed by the server from the saved settings. Discounts are capped by role (barbers 10 % by default, front desk 20 %).

What each person sees of the others (TEAM-01):
- `report.shop` is the owner's and the managers' only, for good: no switch gives it to a barber, so every colleague's revenue, commission, rates and tips, the sales and VAT exports with clients' names, the tickets on a client file and every owner read gated on it stay theirs. A test pins that a barber gets 403 on the sales, VAT, commissions, clients and journal exports under every team setting.
- « Ce que chacun voit des autres » (`team.teamView`): **Rien** (own figures only), **Le salon** (default: the month goal reached and the salon's fill, in %, never in euros) or **Toute l’équipe** (`report.team`: each barber's revenue, visits, fill, rebooking, no-shows and average ticket, never commission, rates or tips). A salon whose journal still has the old « Voir le chiffre du salon » switch on and never chose a view reads as **Toute l’équipe**: the closest match that leaks no export. Choosing a view retires the old switch.
- The month goal reaches the owner and managers only; the warnings that stop tonight's Z reach whoever may close the day; the server's own set-up warnings, the owner only.
- The live feed names the chair of every booking and ticket line (`staffId`). A deposit or online payment shows to the till (`sale.all`) and to the barber whose client it is, not to his colleagues; the Z amounts to `closure` or `report.shop` only.
- The desk (no chair, no `report.shop`) sees the whole salon's appointment counts and fill on the agenda, never an amount.
- Nobody changes his own role, and only the owner changes his own commission (`self_commission`, « Ta commission se règle avec le gérant. »). When anyone but the owner changes a colleague's commission or role, or sets a PIN or password, the same command records `team.changed` (ids, rates or role codes, no personal data) and the owner's feed says so: « Frank a changé la commission de JKut : 40 → 45 % ».

## Signing in

- **Owner and managers**: e-mail and password (10 characters minimum), from anywhere. Optional 30-day session.
- **Barbers and front desk**: a 4 to 6 digit PIN, **only on devices the owner enrolled** (Réglages › Appareils) **or on their own linked phone** (below). A PIN typed on any other browser is refused. Obvious PINs (0000, 1234) are refused.
- Passwords and PINs are hashed with **scrypt** (N = 32768, r = 8, p = 1, random salt); comparisons are constant-time, and a dummy hash is computed for unknown accounts so timing reveals nothing.
- **Rate limits**: 6 failed logins per account per 15 minutes, 5 failed PINs per person per device per 5 minutes, global limits per IP. They count failures only, so a busy shop is never locked out. The counters live in the instance's memory: on several instances they are per instance, which still bounds guessing to a handful of tries per minute.
- PIN sessions lock after 4 minutes of inactivity (a shared tablet), last 12 hours at most, and are tied to the device.

### Personal phones (TEAM-02)

A barber can use the Comptoir on his own phone without a password, with the same device cookie and PIN as the salon's tablet:
- **Linking**: from Mon compte (or the owner from Équipe › Accès), `POST /api/v1/staff/:id/phone-link` issues a link `/comptoir/lier/<staffId~exp~nonce>.<HMAC>` shown as a QR code. It is signed with `SESSION_SECRET`, valid **10 minutes** and **single use**: its nonce is recorded (`phone.linkIssued`, ids only) and `device.enrolled` names it, so a second use answers 409 and a late one 410 (one command checks both under the journal's compare-and-swap, so two phones racing get one device). Only the person himself or a holder of `team` can issue one (for someone who himself holds `team` or `devices`, only a holder of `devices`: a manager never links the owner's phone), only while `team.personalPhones` is on, and only for someone who has a PIN. A salon post that opens the link is refused (it would lose its own device cookie).
- **The device**: `POST /api/auth/link` sets the usual `lx_d` cookie (HttpOnly, SameSite=Strict, 400 days; the server keeps its SHA-256) on a device marked `personal` with its `staffId`. On it, `/api/auth/state` offers that person alone and any other PIN is refused (403 `not_yours`).
- **The session**: his PIN there opens a session signed `ph: 1`, 30 days at most, refused after **12 hours** without a request (a salon tablet: 10 minutes), and only while the device exists, is not revoked, is his and personal phones are allowed: removing the phone or turning `team.personalPhones` off ends it at the next request. The Comptoir's 4-minute lock does not run on it. Rate limits are the PIN's (5 failures per person per device per 5 minutes, in memory), and **10 wrong codes in a row remove the phone**: they are counted in the journal (`phone.pinMissed`, reset by the right code), so no restart or other instance resets them; the phone then needs a fresh QR, and the owner and the person see « Téléphone de JKut retiré après 10 codes faux » in the feed. A 4-digit code has a 1-in-1000 chance of falling before that.
- **Revocation**: by the person himself (Mon compte › Mes téléphones), by the owner or a `team` holder (Équipe › Accès), or by the owner in Réglages › Appareils. « Me déconnecter partout » ends its sessions too. A lost phone holds a device cookie and an open session for up to 12 hours after its last use; after that the PIN is needed, with 10 tries before the phone is removed. Removing it (or « Oublier cet appareil » on the phone itself, which removes it too) voids both at the next request. Archiving a member removes his phones and cuts his calendar feed, so reactivating him brings neither back.
- **The feed**: « JKut a lié un téléphone (iPhone de JKut) » reaches the owner (`team`) and the person, so a phone linked without him knowing is seen.
- **His photo**: a 192 px JPEG resized in the browser, at most 24 KB, its magic bytes checked (JPEG or WebP only). The bytes travel in the pii of `staff.photo` (the chain holds a version number); a new photo, its removal or his archiving redacts every earlier copy from the store (`staffRedact`, core/engine.js), as an erasure does. It is served to signed-in staff (`/api/v1/staff/:id/photo`) and to the sign-in screen of a salon device (`/api/auth/photo/:id`, the linked phone's own person only), never to the public site.
- **His agenda in his phone's calendar** (`team.staffCalendar`): `GET /api/cal/team/<staffId~gen>.<HMAC>.ics`, a webcal feed fetched by Apple's or Google's servers. It holds his appointments from 7 days back to 45 days ahead: the services, the visit count (« 1re visite »), « réservé en ligne » and cancellations; the client's first name only when he turns « Afficher le prénom » on (`calName`); never a surname or initial, a phone number, a note, a price or a link. « Nouveau lien » moves the generation above any given before, so the old address answers 404 for good; off, archived or the setting off, 404 too.

### Mon espace and cut notes (TEAM-04)

- **One read, computed for the person who asks** (`GET /api/v1/espace`, `server/domain/espace.js`, capability `agenda.own`, only for someone with a chair: the desk gets 409 `no_chair`). It holds his own appointments, his own clients' first name and last initial, his own figures (`report.own`: Chiffre réalisé, commission, tips, panier) and his goal (unless the owner hides goals from barbers), and the salon only in percent, with names only when the owner chose « chacun voit les autres » (`report.team`). No colleague's money, no client's number or e-mail, no appointment of another chair. It is memoised per journal version, person and day, for the current minute only (one entry per key, at most 500).
- **Cut notes** (`POST /api/v1/appointments/:id/cut-note`, `server/commands/cutnotes.js`): written by the appointment's barber or by someone who edits every booking (`needChair`), 1 to 280 characters, while the client is in the chair or done, at most 14 days after the visit, on a client file (a name-only passage has none). The text travels in the `pii` of `cut.noted`, never in the chained `data`, which holds the appointment, the file (`data.cid`), the barber of the cut (`staffId`), who wrote it (`by`: the desk or the owner when it was not the barber) and the day. A second note on the same appointment replaces the first in what is shown; the earlier wording stays in the journal and in `prev` (five at most). Any barber with `client.view` reads the last three on the client's next visit and on his file (`GET /api/v1/clients/:id/cut-notes`), under the barber of the cut, with « écrit par » the writer when it was somebody else (`mine` is true for the writer); the placeholder tells them not to write health information. The data export gives them under `notesDeCoupe`.
- **Erasure and merges**: `s.cutNotes` (last 20 per file) follows merged files through `fileIds`; `client.erased` empties it, and the engine redacts the `pii` of the file's `cut.noted` events in the store like any other event of the file, so an erased client keeps no note.
- **Preferences**: the order and the hidden cards of Mon espace are the person's own (`prefs.cards`, `prefs.hidden`, `PATCH /api/v1/prefs`); on a shared salon post the amounts start hidden (`prefs.blur`) and a tap shows them for 30 seconds.

## Sessions and cookies

- `lx_s` (session) and `lx_d` (device): **HttpOnly, Secure, SameSite=Strict**, HMAC-SHA256 signed with `SESSION_SECRET`. The device token is stored server-side as a SHA-256 hash only.
- `lx_c` (a client's own space, AC-01): **HttpOnly, Secure, SameSite=Lax**, signed with `SESSION_SECRET` under another label (`client:`, the staff's is `session:`), so neither cookie passes for the other. See [Espace client](#espace-client).
- Each request re-checks the session against the live state: removing a person, revoking their sessions ("Déconnecter partout"), changing their password, or revoking a device takes effect on the next request.
- Writes must be same-origin (Sec-Fetch-Site / Origin) and JSON: a page on another site cannot forge a request, on top of SameSite=Strict.

## Headers

`Strict-Transport-Security` (2 years), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (no camera, microphone, geolocation). The Comptoir and the client pages add a strict **Content-Security-Policy** (scripts from the site only, no inline script, no framing, forms only to the site and Stripe), `X-Frame-Options: DENY` and `Cross-Origin-Opener-Policy`. `/comptoir` is `noindex`.

## Client links

"Mon rendez-vous", receipts and waiting-list offers are reached through links signed with HMAC (`code.signature`). They expose no other appointment, cannot be guessed, and show no personal data beyond the client's first name.

The referrer's link (FID-02, `/?parrain=<file id>.<HMAC 'ref'>`, server/http/routes-loyalty.js): `GET /api/public/parrain/:token` (30 a minute per IP) shows his first name and the welcome offer, only while referral is on and his file exists; a booking carrying it records the referral as the system, never blocking the booking, and only for a file that booking created (24 h), never seen before, with another number (last 8 digits) and e-mail than the referrer's, at most `perYear` referrals by the same referrer per calendar year (those rewarded, and those still within the referee's 60 days, so junk bookings through a link cannot use up his year for good); a file that opted out of the card takes no part. The answer to the booking says only `referral: { ok, why }`. The link between the two persons is erased with either of them (`client.erased.drop`).

`/mon-rendez-vous` has no account behind it: `POST /api/public/lookup {phone}` (server/http/routes-client.js) texts the links of the client's next two appointments, and only to the number on file (an erased client or a merged file's old number gets nothing). Whoever typed the number learns nothing: the answer is the same words and status for a known, unknown or erased number, and it leaves after 450 to 650 ms whatever the store, because the journal write runs after it (`waitUntil`). Limits: 10 asks per IP per hour (then a 429, which says nothing about the number), 3 per number per day in the instance's memory, and 3 texts per client per day kept in the journal across instances; past them the answer stays the same and nothing is sent. Both are shared by every page that texts a link or a code on demand (server/domain/linkcap.js, FID-01: the key `link|<ip>` and `linkSendsToday`, counting lookup, sign-in codes, membership and space links, access invites together), so three pages do not make nine texts; past them the answer stays the same and nothing is sent. The text is a service text asked for by the person holding the phone, so it leaves at once, quiet hours included: at worst a stranger who knows the number makes the salon text it three times in a day, with links only that phone can use.

## Public endpoints

Everything under `/api/v1/*` needs a session and a capability. The routes below answer without one, each with its own guard:

| Endpoint | Who calls it | Guard | What it can change |
|---|---|---|---|
| `/api/public/*` | the site and the client pages | same-origin writes, rate limits, signed links for one booking | holds, bookings, moves and cancellations of the client's own booking |
| `/api/public/account/*`, `/api/me/*` | the client space (/moi) | see [Espace client](#espace-client): the same answer for every number, a code by SMS to the number on file only, limits per device, per number and per file, the cookie `lx_c` checked against the file at every request | a sign-in on the client's own file; signing out, closing his space |
| `/api/auth/*`, `/api/setup*` | the sign-in and setup screens | rate limits on failures; setup and restore need `SETUP_TOKEN` and an empty salon | sessions; the first owner, or a restore |
| `POST /api/pay/stripe/webhook` (alias `/api/stripe/webhook`) | Stripe | signature with one of the secrets in `STRIPE_WEBHOOK_SECRET` (5-minute tolerance, constant time); any other provider name answers 404; idempotent per object | payments only: paid, expired, refunds made at Stripe, disputes, payouts and their fees |
| `/api/public/memberships*` (PAY-03) | the site, /resilier, the member's page | subscribe 5 a minute and 20 an hour per IP; « send me my link » shares `link\|<ip>` and the file's 3 a day, same words and about the same time for a known or unknown number or address; the cancellation without the link 5 an hour per IP, 3 a day per address, the same answer whatever it found; the member's page needs a signed link that expires (`mb_…~<expiry>.<signature>`, 7 days in a text, 1 hour when asked: a stretched expiry breaks the signature; 410 once past) | the member's own contract only: cancel, withdraw (the law's amount, never one typed), the card page (Stripe's); a cancellation without the link is recorded unverified and Stripe is only told when the salon confirms |
| `GET /api/cron/tick` | the external scheduler | `Authorization: Bearer <CRON_SECRET>` | runs the background work, as the scheduler does |
| `POST /api/sms/webhook?k=…` | the SMS provider (Brevo, Twilio, or the salon's phone through SMS Gateway for Android) | CSRF check off (the provider is another site); the key `k` in the query string is derived from `CRON_SECRET` (HMAC, `webhookKey` in server/messaging/sms.js), compared in constant time; 120 calls per minute per IP; unknown without `CRON_SECRET` | **only consent**: a STOP reply turns that client's offers off (`marketing: false`, source `stop`) and closes their offers still waiting; the review request (a « relation » text) stops too, also one already waiting for the morning (skipped as it would leave). Service texts, bookings and files are never touched; an unknown number changes nothing. From the salon's phone also: a client's other answer becomes a request in Relances › Demandes (kind `sms`, its words and number in pii, recorded once per event id; the chained data names only the template and id of the text it answers), a mere « ok » to a review request, reminder or receipt filed by itself, and a delivery report marks that text failed or delivered. Nothing else |

Provider credentials (MSG-02): `BREVO_API_KEY` (SMS, e-mail, WhatsApp), `TWILIO_AUTH_TOKEN` and `SMSGATE_USERNAME`/`SMSGATE_PASSWORD` (the SMS Gateway app's cloud account, shown on its Home tab) live in Vercel only (type Sensitive). The Comptoir's Canal d'envoi (`GET /api/v1/messages/channels`, owner) says whether each one is set and never returns a key, a password or a username; the test text (`POST /api/v1/messages/channels/test`) goes only to a French mobile, three an hour per route, and writes nothing to the journal. The salon phone's own webhook signature (`X-Signature`) is not checked: the key `k` in the address the owner registers plays that role, as for Brevo. Whoever holds the SMS Gateway credentials can send texts from the salon's SIM: change them in the app (and in Vercel) if the phone or the account leaks. No WhatsApp Web automation is ever used (it breaks WhatsApp's terms and gets the number banned): only Brevo's official WhatsApp API with templates approved by Meta.

## Espace client

AC-01. A client may open a space on his file (`/moi`): his bookings to come, his visits and receipts, what he holds. **The file is the client**: an account is only a verified sign-in attached to it. There is no password and no sign-up form; a file is born from a first booking or at the salon, so a sign-in never texts a number the salon does not already know (nothing to pump, nothing new to enumerate). Guest booking is not touched: nothing on the site needs an account. Off in production (`settings.accounts.enabled`) until the SMS route is tested and the switch to the new site is done; on in the demo.

- **Codes that are never stored.** `POST /api/public/account/start {phone}` queues a text whose body says `{code}`; the six digits are `HMAC-SHA256(SESSION_SECRET, 'otp:' + message id)` (the first 4 bytes as an unsigned integer, mod 10⁶), filled in only as the text leaves (`server/domain/otp.js`, through the scheduler's `FILLERS`). The outbox, an export and the journal only ever show `{code}`; there is no challenge event and no hash to leak, and every instance computes the same code. A provider's error is masked for these texts (`SECRET_TEMPLATES`). The text's words are fixed in the code, not in the editable templates, and end with the WebOTP line `@host #code`. A code lives 10 minutes and works once (`account.signedIn` and `account.codeBurned` mark it used).
- **The same answer for every number**: a known, unknown, erased or merged-away number get the same words and status, after 450 to 650 ms whatever the store; the work runs after the answer. `verify` waits as long before it answers, so the write of a wrong try against a live code does not tell a known number from an unknown one. Only the number on file receives a code. `keep` (from a booking's `/r/` link: « Garde ton espace », or the salon's invite `acc` = `cid~expiry`, signed, 48 hours) may say where the code went (`06 •• •• •• 78`), since the link's holder already knows that booking or got the link on that number. Either link proves the phone only, like a code: it never skips the first-name question. A code text that leaves after its code died (no SMS route for a while) says so instead of carrying dead digits.
- **Limits, per instance and in the journal.** In each instance's memory: the shared `link|<ip>` key (10 asks an hour per device, every « send me a link » page together), 3 asks per number per day, 5 wrong codes per file per 10 minutes and 20 per device per hour (then « Trop d’essais »), keyed on the file the number resolves to, not on the string typed. In the journal, so every instance agrees: 3 codes per file per day, within the 3 link texts a file may receive a day (`linkSendsToday`); each wrong try against a live code is an `account.codeMissed` with a deterministic id (`acm_<msgId>_<k>`), and a code with 5 of them is dead wherever they were counted; the 5th failure in an instance burns every live code of the file at once (`account.codeBurned`). At worst a stranger who knows a number makes the salon text it three times a day, with a code only that phone sees.
- **The cookie `lx_c`** = base64url `{ sid, cid, ph, iat, exp }` + HMAC. `SameSite=Lax`, not Strict, so `/moi` opened from an SMS or a mail arrives signed in; every write still needs a same-origin request (Sec-Fetch-Site / Origin), which a cross-site page cannot forge. It lasts `accounts.sessionDays` (180 days by default) and slides once a week.
- **Bound to the phone.** `ph` is a 16-character HMAC tag of the number at sign-in. Each request follows the file's merges, refuses an erased file, compares the file's current number's tag with `ph`, and needs an open account with nothing revoked since the cookie. So the salon changing or detaching the number (« Numéro réattribué ? Détacher ce numéro », `agenda.edit`: the number leaves the file, the next booker gets a fresh one), a merge into a file with another number, « Déconnecter tous mes appareils » (the client, or the salon with `client.edit`), « Supprimer mon espace » and an erasure each end every session at once. A space closed and opened again keeps its fence, and no cookie from before the closing comes back.
- **The fence, for a number that changed hands.** At the first opening, after the right code, the person also types his first name: its first word against the file's, without accents or case, in any script (Jean / Jean-Pierre); a shortened name only from 4 letters (Alex / Alexandre), so « Meh » or « Mar » never sweep a name. A booking that just created the file counts as named. Three wrong names since the file's last opening (in the journal, `s.nameMisses`, whatever the day or the code) open the space anyway, but **fenced and unnamed**. Fenced too: a file not seen at the salon for longer than `accounts.fenceDays` (180 days: its last visit done or under way, its last ticket, its creation; a booking, even for today, is not a visit, since the new holder of a number books before he opens the space), or a file brought from WordPress never seen here. A fenced space shows nothing from before the day it opened (`historyFrom`: no old visit, receipt, carnet, card, booking or rhythm), and neither the last name nor the birthday on the file; an unnamed one shows not even the first name (not the one the person could not give), nor when the file said yes to offers. The salon's feed says « Espace ouvert sur une fiche inactive » to whoever sees the files (`account.fenceOpened`; a mere sign-in is not in the feed), and the export and the erasure request (AC-02) need a space neither fenced nor unnamed. A space opened before keeps its fence, **except after a long silence on both sides**: no sign-in and no visit for `fenceDays`, the number may have changed hands since, so the question comes back and the fence starts again from that day (`account.signedIn` with `refenced`). The file's e-mail, if any, is told of the first opening (« Si c’est toi, rien à faire. Sinon, appelle le salon »).
- **Commands as the client**: the actor is `{ t: 'client', id: 'moi', n: '' }`, never a name; a client route takes the file from the session (`runAs`, `server/http/me-kit.js`), never from the body; its idempotency key is the client's (`'me' + cid + ':' + x-request-id`). The sign-in routes, before any session, run through `runSigningIn` (same actor, no file).
- **The demo** sends no text. « Essayer avec un client de démo » signs in as the persona (the seeded regular with the most visits and a booking to come), whose writes answer ok without being recorded, so a visitor never changes the showcase for the next: signing in with its number and code is never asked the first name nor fenced, re-openings write nothing, and every visitor shares its live code (outside the daily caps, the texts being simulated). A code is shown on the page only for the persona's number, or after a visitor's own booking that created its file just now: another visitor's real number typed there opens nothing. What visitors type is erased two hours after their file was created (`server/commands/steps/demo-purge.js`); a file whose erasure is refused waits an hour before the next try, so it never holds the others back.
- **What a client changes of himself (AC-02, `server/http/routes-moi.js`, `server/commands/me.js`).** Every route is behind `requireMe` (401 without `lx_c`; a staff session alone opens none), takes the file from the session, and writes through `runAs`; each emits one event only when something changed, and 60 writes an hour per client is the ceiling. `PATCH /api/me/profile` takes first name, last name and birthday (a phone or an e-mail in the body is dropped: the salon changes those), `PATCH /api/me/consent` the two switches (the offers keep their proof: `marketingSrc: 'espace'`, `marketingAt`), `PATCH /api/me/prefs` the preferred barber (an active chair only). A space opened on a file that may have changed hands (`fenced`, or the first name not given) **reads and writes nothing of the file's identity**: profile, export and erasure request answer 403 « Pour ça, passe au salon. »; the two switches and the barber stay possible, they are about this phone. The demo's persona answers « Démo : rien n’est changé » and writes nothing.
- **A copy of his data goes by e-mail, never as a download.** `POST /api/me/export` queues one `dataExport` mail (a `requested` text) to the address the salon holds, with the JSON of the salon's own export (`clientExport`, plus an `espace` block) attached as a `.txt` (Brevo's list of attachable extensions has no `.json`); the answer only says « Envoyé à k•••@gmail.com ». Whoever holds an open phone cannot walk away with the file, and the address is the file's, never one named in the request. 5 asks an hour and 5 mails a day per client. The attachment lives in the journal's pii like the mail, in memory and in the store, until the file is erased (only the projection's copy is dropped once the mail has left, `core/state.js`): each export adds one copy of the client's data to the pii and to the backups, which is why they are capped (5 an hour and a day, 2.5 MB). Nothing can be sent when there is no e-mail on file, when e-mails are off in Réglages, or when the file is too big to attach: the client is told which (« Pas d’e-mail sur ta fiche : demande-le au salon. » or « Ta demande est notée »), the owner gets a mail (`owner_export`, with the reason) and, when no mail can leave, a line in the feed (`account.exportAsked`, once a day), so the request is never lost. The owner's alert mails (`owner_*`) name the client's file but are left out of that file's own export and message list.
- **Erasure is requested, the owner erases.** `POST /api/me/erase-request` writes one `account.eraseRequested` per space (a second tap is told it is already there), mails the owner (`owner_erase`, first name only, carrying the file's id so erasing it blanks the mail) and puts a line in the feed of whoever holds `client.erase`. The request outlives « Supprimer mon espace » (`accountPast` keeps `eraseAt`) until the file is erased; the owner's mail is keyed per day, so a new request is never swallowed by an old one. The file is not touched: Clients › fiche › Effacer keeps its guard on what is still open. The promise to the client is « sous un mois »; no confirmation text is sent, since the number leaves with the file.
- **The salon's invite** (`POST /api/v1/clients/:id/account/invite`, `client.edit`) texts the file's own number a `/moi?garder=` link carrying an `acc` token (`cid~expiry`, signed, 48 h): it proves the number it went to, nothing more, and asks the first name like any first opening. It counts in the 3 link texts a file gets a day (`linkSendsToday`).

## Payments

- **Stripe Checkout**: card data never touches the salon's server. Amounts are computed on the server; the webhook is verified (signature, 5-minute tolerance, constant-time comparison) and idempotent. Refunds go through Stripe with an idempotency key, through the provider each payment used (`providerFor`).
- Stripe's customer and card ids tie a person to a card: they travel in the pii of `payment.succeeded` under the client's file (erased with it), and are not kept at all when no file is known (a QR at the till). Payment, charge, payout and dispute refs (`pi_`, `ch_`, `po_`, `du_`) stay in the chain: reconciliation needs them, and they name no one. Stripe's error texts are never shown to a client.
- Keeping or refunding a deposit whose visit will not happen (Caisse › À traiter, `POST /api/v1/payments/:id/keep|refund`) needs `sale.refund` (owner, manager); each is refused once the deposit is on a ticket or refunded, and a replayed request gets its first answer. A till refund is keyed at Stripe by its request id, so a replay never refunds twice.
- The demo refuses live Stripe keys, so a demo can never charge anyone.
- At the till, card payments go through the salon's own terminal; the Comptoir records them.
- **Stripe Billing** (PAY-03): every billing notice is re-read from Stripe before a command runs, so a forged-looking or replayed notice cannot write what Stripe does not hold; a subscription is matched by its id or our metadata, never by a name or number. Money no contract covers is refunded at once (keyed by the invoice). A subscribe request for a number that already has a running membership answers « Tu as déjà un abonnement » (the one thing the site tells about a number: the link goes to that number only). A dispute holds the billing (pause_collection void) and stops the covered cuts until it is won. An offer from the counter is texted only with `member.manage` (a barber shows the QR code, `client.edit`), and a barber reads an end for want of payment as a plain end.
- **Memberships** (PAY-02): only the provider's webhook or the scheduler records a paid or refused invoice and the end (`server/commands/memberships.js`); a checkout is recorded by them too, or at the counter by a staff member with `client.edit` (channel `salon`), who learns nothing of another file from a known reference (`{ already: true }` only). A month is rung up by the system only, never at the till, and its ticket is not refunded at the till while the contract runs (the withdrawal or the cancellation ends it first). A client cancels or withdraws only on his own file, as the route vouches for it in the ctx (`meta.me.cid` from AC-01's `runAs`, or `meta.memberId` from a verified member link), never from a cid in the body; he never sets the refund (always the first month less the cuts taken) nor speaks for the salon. The salon needs `member.manage` (owner and manager) to cancel, withdraw with its own amount or give a cut the plan does not cover today (`force`, recorded on `member.used`). A barber sees a client's « abonné » badge and cuts, not the card label nor a payment in trouble, and no membership line in the feed. The processor's references (customer, subscription, card label) live in the pii of `member.activated`, never in the chain, and are not written at all under a file erased before the first payment; every member event carries `data.cid`. A checkout never paid leaves a plain client file (first name, number) with nothing in it: the retention purge of inactive files covers it.

- **The member's side** (PAY-04): `/abo/<link>` (the member page, PAY-03's signed link that expires) and `/moi` (`/api/me/membership*`, `server/http/routes-me-membership.js`: `requireMe` + `runAs`, the member is always `memberOf(s, me.cid)`, never an id or a number from the body; the demo's persona reads but writes nothing). A covered cut books with no deposit only on a **verified path**: the member page's « Réserver ma coupe » carries a booking-only signed link (`/?reserver&mbr=…`, kind `mbk`, 1 h, read only by `POST /api/public/bookings`: it cannot open the member page, cancel, withdraw or change the card, since it rides in a URL and the demo's persona hands it to every visitor), and only for the file the typed number finds; a guest typing a member's number gets the usual deposit and no member words, and a forged, expired or member-page (`mbr` kind) link is ignored (the till still applies the membership). The welcome e-mail's links live until the day after the withdrawal deadline (its « Renoncer au contrat ici »), the other texts' a week. A booking consumes nothing: the member's other bookings to come in the month count as taken, so a member cannot stack free slots. The acknowledgement to keep (`GET /api/public/memberships/<link>/ack/<kind>`, `/api/me/membership/ack/<kind>`) is a downloaded HTML file with the dates and what stays included, only for what that member was acknowledged; every value goes through an HTML escape. `/resilier` is public, free and needs no account (L.215-1-1): a number or an e-mail sends the link to both channels on file (PAY-03's same answer for any input), its link opens on the cancellation's recap, and without either the first name and the subscription's e-mail record a cancellation the salon confirms. It runs under the client pages' strict CSP (no inline script: `public/resilier.js`). A signed-in client subscribes on his own file: the space's number, never the one typed.

What is still open is listed first (bookings to come, carnet cuts, gift card balance): the bookings are cancelled and the client texted before the number goes. Personal data is removed from the state and from every event; tickets stay in the accounts without the name; the journal still verifies. The `client.erased` event keeps only keyed hashes of the number and e-mail (HMAC-SHA256 under a key derived from `SESSION_SECRET`, cut to 32 hex characters), so a re-run of the WordPress import skips the rows of the person from before the erasure (« client effacé à sa demande »); a booking the old site recorded after it comes in (the person came back). A plain hash would not do: the chain keeps it for good, and every French mobile can be hashed in minutes. ### Jour J (WP-10)

Réglages › Reprendre WordPress › Jour J records the cut-over in three events with no personal data: `bascule.frozen`, `bascule.switched` (with the owner's reason, 200 characters, when he forces it: write no name in it), `bascule.rolledback` (the owner's reason for taking the switch back, 200 characters: no name either) and `bascule.ticked` (an item name). **The hold**: while a production salon has a WordPress run and `bascule.switched` has not been written, `dispatch()` (server/http/scheduler.js) does not claim a text that has a client file (`cid`), by any channel and whatever provider an early variable plugged in. It never holds what the client asked for himself (`requested`), a contract's acknowledgement (`legal`), nor an owner-addressed text (no `cid`, or `owner`); the 6-hour expiry is unchanged, so what waited through the night never leaves. A new way to send must go through `dispatch()` or call `cutoverHold`. The checks (GET `/api/v1/bascule`) are owner-only (`settings`) and make three kinds of outgoing requests, none with the salon's credentials: a DNS lookup of the domain, the old addresses on the salon's own public address (`redirect: 'manual'`, 8 s each, 6 at a time), and one read of `https://ancien.<domain>/` (https only; the name is resolved first and nothing is read when it has no address or any of its addresses is private, IPv4-mapped IPv6 included; no redirect followed; the body is read as a stream and dropped after 64 KB; 8 s. The request resolves the name again itself, so a name that changes answer between the two lookups is not excluded: the answer only reveals a status code and a noindex flag, to the owner). The domain is the owner's own input, checked as a hostname (no IP, no port, no path). WP-07's `safefetch` can take over the last one when it ships. `GET /api/v1/bascule/since` is a CSV with the names, numbers and e-mails of the clients who booked here since the freeze, and still from the freeze once the switch is made (`Cache-Control: no-store`, owner only): it is personal data in the owner's hands, to be deleted after it has been typed into WordPress.

## Fiscal note (France)

**Le Comptoir is a management till (« caisse de gestion »), not the salon's legal cash register.** In production the Caisse page says so on every tab: « Caisse de gestion : le ticket légal sort de ta caisse certifiée. » The demo does not show it.

Since 2018, software that records sales for clients who are not businesses must guarantee **inalterability, security, preservation and archiving** of the data (anti-fraud VAT law, art. 286, I-3° bis CGI). The 2025 finance law (loi n° 2025-127 du 14 février 2025) appears to have ended the publisher's self-certification: the only proof left is a **certificate issued by an accredited body**, in practice NF525 (issued by Infocert) or the LNE's certification. The salon's accountant is to confirm this reading. Until a certificate exists, the salon's current certified till stays the legal one: every sale is also rung up there and the client's legal ticket comes from it. Le Comptoir's tickets are management records: the day's figures, the barbers' commissions, the client's history and follow-ups.

What Le Comptoir already has: a SHA-256 chained journal, numbered tickets without gaps, credit notes instead of edits, a sealed daily Z with a perpetual grand total, and an archive export verifiable offline. What a certification would still need, at least:

- **Signed tickets**: each ticket, and the grand totals, carry an electronic signature, not only a link in the chain.
- **Monthly and annual closures**, each with its own perpetual totals, on top of the daily Z.
- **A duplicata counter**: every reprint of a ticket is numbered and marked « duplicata », and the count is kept.
- **A technical event log (JET)**: start and stop, errors, archives, version changes and data purges, chained like the journal.
- **Signed archives**: periodic archives (at least yearly) sealed with a signature, kept 6 years.
- Then the audit itself, by the accredited body, for each published version.

The risk if Le Comptoir is used as the till without a certificate: a **7 500 € fine per system** (art. 1770 duodecies CGI), with 60 days to put a compliant till in place after a tax inspection. Nothing in this repository changes the Z for this; the work above is a separate project, listed in the [roadmap](roadmap.md#before-go-live).

## Signed closures and the technical log

CPT-01a. Every Z, every month closure (the sum of its Z, with the period's grand total and the perpetual totals, BOFiP §170) and every year closure (the month numbered `fiscal.yearEndMonth` closes the year too) is sealed on the journal hash like a Z, then **signed** by the tick that follows (`server/commands/steps/fiscal.js`): Ed25519 over `{ ref, kind, of, seal, digest }`, where `digest` is the SHA-256 of the closure's record. `verifySeal` (`server/domain/fiscal.js`) checks one against a public key. The chain proves the journal was not edited by someone who could not recompute it; the signature, with a key kept outside the database, proves the closures were not rewritten by someone who could.

- **The key**: `LX_SIGN_KEY` (32 bytes, base64; see [operations](operations.md#environment-variables)). Without it a key is generated once and kept with the data (`source: store`): it signs, but whoever holds the database holds the key, so the owner's warnings say so until the variable is set (Réglages › Données › Système; Mise en route lists it once WP-10 reads the `fiscal` section's `golive`). The demo signs with a fixed, public key (`source: demo`), even when `LX_SIGN_KEY` is set. The key's id (first 16 hex characters of the SHA-256 of the raw public key) and its public key are written to the technical log the first tick they are used; GET `/api/v1/fiscal/log` returns every public key (`keys`), so a signature can be checked without the Comptoir.
- **The anti-rewrite rule**: a closure older than 36 h is signed only if it was already waiting when the current key first appeared (that key's backlog, signed `late`, « signée en retard »). Anything else that old stays « non signée » for good, unless a genuinely new key appears: a backlog is fixed when a key is first logged, so a key already seen (coming back after another, or logged again by whoever rewrites the tail) never gets a second one, and a tail of the journal rewritten and re-sealed cannot be signed quietly. Two deployments with different keys on one database each sign what is fresh with their own, without logging their key again. At most 100 signatures per tick, the fresh ones first. The demo, which writes its own past, signs everything.
- **The technical log** (`tech.logged`, GET `/api/v1/fiscal/log`, owner and managers): each signing key, each software version the first tick it runs (once: a build that runs again, after a rollback or beside another build on one database, is not logged a second time), and each restore. CPT-02 adds archives and exports.
- **The version** (`server/version.js`): `1.0 (a1b2c3d)`, the build being the deployed commit. Bump the **major** on any change to tickets, closures or the journal format (a version whose proof of compliance must be renewed, BOFiP §380), the **minor** for anything else.
- **Replay check**: `node scripts/replay-diff.mjs <journal>` replays a journal copy with the code of the checkout and prints the figures a code change must never move (Z and grand total, month closures, gift card and carnet balances, deposits held, client counts; members and loyalty once they exist). Run it on copies of the demo and production journals with the base and with the merged tip of each wave; any difference (`--compare <earlier output>`) is drift and fails the wave.

## Reporting a problem

Anything that looks like a security issue: stop using the affected feature, note the time, and contact whoever operates the installation. The activity log (Réglages › Journal) shows who did what and from which device.
